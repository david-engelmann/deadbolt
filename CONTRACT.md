# Contract

Deadbolt asks whether an agent can do its work with credentials it never sees, acting through scoped and expiring tokens while the real keys never enter the agent process. This file is the stub contract for the setup slice. It states the setup obligations only, and each obligation is stated so it can fail.

Obligation S1 covers seed integrity. The seed files README.md and LICENSE and .gitignore are present from the first commit, and every later change lands through a pull request rather than a direct push to main. This is covered by inspection of the repository history and by the status section of the README.

Obligation S2 covers the local gate. The test suite runs with cargo test plus the codepoint scan run through cargo, and running it needs no paid service, and the continuous integration workflow runs the same commands as the local gate. This wording is amended by Round 1 slice 1. The setup wording named python and pytest alone and no network access, and the amendment replaces it under the program language ruling of 2026-11-02, which made every repo in the program a Rust crate. The amended gate keeps the no paid service term. It drops the no network access term for one stated reason, a first build fetches the crate dependencies from the public crates.io registry, and the tests themselves then run with no network access. This is covered by the tests in the tests folder and by the workflow in the .github folder.

Obligation S3 covers honest status. The README status section records the seed state and the contract state truthfully and it reports closed perfection rounds as 0 of 100 until a full cycle of work and audit and review and red team and approval has closed. This is covered by inspection of the README against this contract and against the repository history.

Obligation S4 covers synthetic content only. Every fixture and every example in this repository is synthetic and written for this repo, and no file carries a real trace or a real transcript or a real name or any private operational detail. This is covered by inspection of the repository contents before any push.

Obligation S5 covers the canonical agents file. The part of AGENTS.md above the marked line is identical to the canonical template for the program, and only the repo annex below the marked line differs for deadbolt. This is covered by tests in the tests folder that pin the SHA-256 digest of the part above the marked line and check the marked line and the annex.

The full contract for deadbolt is the first build act of this repo and it lands with the first slice. This stub is not the full contract, and no feature claim for deadbolt rests on this stub.

## The full contract, Round 1 slice 1

The stub above stands as the record of the setup state, with the one amendment stated inside obligation S2 itself. What follows is the full contract the stub promised, landed as the first build act of this repo in Round 1 slice 1. Slice 1 builds the broker core as a Rust library crate with a thin command line binary over one local state file. It runs no network service, integrates with no proxy or harness, and brokers only for callers who share the machine and the filesystem.

### Probe preamble

The obligations below rest on behaviour probed on this machine rather than on habit. The toolchain is cargo 1.91.1 and rustc 1.91.1. A scratch crate depending on serde and serde_json and sha2 and fs2 and getrandom resolved every dependency from the crates.io registry and built and ran clean, so the broker is built on those crates and on no hand rolled JSON or hash code.

The getrandom crate filled 32 bytes from the operating system random source in about four microseconds. The fs2 exclusive lock blocked a second handle that tried to take the lock while it was held and allowed it after release. A rename within one directory preserved a mode of 0600 set on the temporary file, and the mode bits read back as 0600 for a process running as root, so the permission gate can read bits rather than attempt access. Eight workers each performing 25 increments as a locked read and modify and rename publish against one document produced a final count of exactly 200, and a reader thread parsing the document throughout observed 1626 reads with zero parse failures, so publication by rename never shows a torn document on this machine.

Plain serde_json parsing accepts a document with a duplicated key into an untyped value and keeps the last value, so strict reading cannot rest on untyped parsing. Parsing the same document into the typed state structures refuses it, because the derived readers reject a repeated field, and they reject a field the format does not name when the structure denies unknown fields. A 5000 digit integer refuses with a number out of range error rather than parsing, an integer past the u64 range refuses as a type error, and a fractional number refuses for an integer field. The strict reader of obligation DK-2 is built from those typed structures plus the cross field checks of DK-2 itself.

### Obligation DK-1 covers the state document and its publication

The broker keeps credentials and grants and the audit trail in one JSON document whose format field names deadbolt-state/1. Every change is published by writing the whole document to a temporary file in the same directory, setting its mode to owner only before the write, syncing it, and renaming it over the state file, and every act happens while holding one exclusive advisory lock on a lock file standing beside the state file. The lock file is the standing companion file of the broker. Opening the broker creates it whether or not a state file stands, it is created with mode 0600 like the state file, and it carries no credential data and no record of any act. A grant and the audit record of the grant land in the same rename, so the document never shows one without the other. A state file that does not stand is read as an empty broker, and an act that changes nothing and records nothing creates no state file.

### Obligation DK-2 covers strict reading

A state document that stands must parse as the one format and nothing else. A duplicated key at any level, a field the format does not name, a value of the wrong type, and a number outside the range of its field each refuse as typed corruption. Cross field invariants are validated on every read. Credential names stand unique, grant ids stand unique, token hashes stand unique, the audit sequence stands gapless from one, and every live grant names a credential that stands. A state that fails any of this blocks every operation with the corruption named, and the broker never resets or truncates or repairs a state file on its own.

### Obligation DK-3 covers enrollment

Enroll names a credential, its value, and its allowed scopes, and each scope is one resource and one action stated as a pair. The command line takes the value from a named file only and never from an argument, and the library operation takes the value as data. The value must be one nonempty line of text, and an enroll that names no scope or repeats a scope fails validation of the request shape. Enrolling a name that already stands is refused against the loaded state.

### Obligation DK-4 covers retirement

Retire names a credential and removes it, and every live grant for that credential ends in the same act with the retirement named as its reason. Retiring a name that does not stand is refused. A grant ended by retirement redeems never again, including at instants inside its window.

### Obligation DK-5 covers granting

Grant names a credential, one scope, a time to live, and optionally the run the grant belongs to. The grant succeeds only when the requested scope equals one of the credential enrolled scopes as a whole pair. On success the caller receives a grant id and the token and the expiry instant, and the state records the grant with the hash of the token and never the token itself. Granting against a credential that does not stand is refused, and granting a scope the credential does not carry is refused.

### Obligation DK-6 covers the token

A token is 32 bytes from the operating system random source, written as 64 lowercase hexadecimal characters. The state stores only the SHA-256 hash of the token text. The token is returned once, by the grant that created it, and no later operation displays it. Redeem finds its grant by hashing the presented token and comparing hashes, and the broker never stores or logs the presented token.

### Obligation DK-7 covers redemption

Redeem presents a token and the scope the caller wants to exercise. When the grant stands live at the presented instant and the presented scope equals the grant scope, redeem returns the credential value and nothing else on its output. Every other outcome is a refusal that names its reason, and the reasons are distinct and checked in one order. Unknown token names the case where no grant carries the presented token hash. Revoked names a grant that has ended by revocation or cutoff or retirement, and it is reported at every instant, including instants before the grant expiry and instants after it. Expired names a grant that stands unended at or after its expiry instant. Scope mismatch names a grant that stands live and unexpired whose scope differs from the presented scope. A grant is live strictly before its expiry instant and dead at it.

### Obligation DK-8 covers revocation and cutoff

Revoke names one grant id and ends that grant. Revoking an id no grant carries is refused, and revoking a grant that already ended is refused with the ending named. Cutoff names a run id and ends every live grant carrying that run id in one act, and it reports how many grants it ended. Cutoff for a run id no grant carries is refused, and a cutoff whose run grants have all already ended succeeds and reports zero. Grants of other runs and grants carrying no run are untouched by a cutoff.

### Obligation DK-9 covers the audit trail

Every act the broker performs against a state it could load is appended to the audit trail in order, enrollments and retirements and grants and redemptions and refusals of grants and redemptions and revocations and cutoffs, each with a sequence number, the instant supplied for the act, the credential name where one is known, the scope where one is in play, the run id where one is in play, and an outcome that names what happened, including the distinct redemption refusal reasons of DK-7. Request shapes that fail validation before the state is opened are caller errors and are never recorded. Acts refused by the permission gate or by corruption are never recorded, because the state they would be recorded in is the state being refused. An act refused against a state file that does not stand is recorded nowhere and creates no state file. The lock file of DK-1 is the standing exception to that sentence, because opening creates it before the broker can know whether a state file stands. The audit trail never carries a credential value or a token or a token hash, and the audit command prints the entries in sequence order and nothing else.

### Obligation DK-10 covers containment of the value

An enrolled value appears in exactly two places, the state file itself and the output of a successful redeem. It appears in no grant output and no audit output and no retire or revoke or cutoff output and no error message, and no operation echoes it back. The token appears in exactly one output, the grant that created it, and afterward only ever as caller input to redeem. The tests grep every command output and every error the broker produces for enrolled values and for live tokens and require their absence everywhere this contract does not name an appearance.

### Obligation DK-11 covers the permission gate

The state file is created with mode 0600, and every published replacement is created with mode 0600 before it is renamed over the old file. On every open the broker reads the state file mode bits, and when any group or other permission bit stands set it refuses every operation with a typed error naming the permission problem, and it writes nothing. The check reads the bits themselves rather than attempting access, so it holds for an operator running as root exactly as for any other operator. Tightening the mode back to owner only restores service with the state intact.

### Obligation DK-12 covers names and bounds

A credential name and a run id and a resource and an action are each safe names, one to 64 characters drawn from letters and digits and dot and underscore and hyphen, starting with a letter or a digit. Instants are whole seconds since the Unix epoch, from 0 to 253402300799. A time to live stands from 1 to 86400 seconds, and a request outside that range fails validation of the request shape before the state is opened. Expiry is computed with checked arithmetic, and an expiry that would pass the largest instant is refused. A number outside the range of its field, in a request or in a stored document, refuses as a typed error or as typed corruption, and the broker never panics on such input and never prints an offending number at the size it arrived.

### Obligation DK-13 covers the command line

The binary is named deadbolt and takes the state file path as a global option. It offers the commands enroll and retire and grant and redeem and revoke and cutoff and audit. Enroll takes the credential value from a named value file only and offers no option that takes the value itself. The command line passes the wall clock UTC instant to every operation and offers no option to override it. Success exits 0. A refusal and a corrupt state and a permission gated state exit 1. A caller error exits 2, and caller errors are bad arguments and an unreadable value file and a request shape that fails validation. A filesystem failure on a path the operator supplied stands in the caller error class as well and exits 2, following the precedent of obligation PC-11 in the portcullis contract, because the operator owns the path and the failure is theirs to repair. Its error line names the path and names the failure as the filesystem refusing it, and never as a fault in the request. Every error prints as one line on standard error. Redeem prints the value and a newline and nothing else.

### Obligation DK-14 covers the limits of slice 1

There is no encryption at rest in slice 1. The state file holds values in plain form behind the permission gate of DK-11, and encryption is named as a later slice because its hard part is custody of the encrypting key, and a cipher whose key sits beside the vault is theatre that would let this repo claim a property it does not hold. Redeem returns the value to its caller, and which local process may call redeem is deployment rather than something the broker proves. The broker trusts caller identity claims, a run id is a label the caller supplies, and cutoff by run is an operator tool and not a proof about who asked. Slice 1 has no network service and no daemon and no proxy or harness integration, no wildcard or prefix or implied scopes, no credential rotation workflow beyond retire and enroll, and no brokering for callers on other machines. Anything beyond these limits is a later slice and is not claimed here.

## Repair note for Round 1 slice 1

The three reviews of this slice found defects, and this repair pass fixes them and is recorded here so the contract and the code tell one story. Retire and cutoff ended grants that had already died by expiry, stamping an ending on them and turning their redemption answer from expired to revoked, and both acts now end only the grants that stand live at the supplied instant under the definition in DK-7, so a grant already dead by expiry keeps no end stamp and keeps answering expired. The strict reader of DK-2 reads the word live with that same definition, judging a grant against the latest instant the document itself records, so a state that retirement leaves behind stays readable by the broker that wrote it. DK-1 and DK-9 now name the lock file as the standing companion file that opening creates, so the creates no file wording of the first build no longer reads against its own design. The lock file is now created with mode 0600 like the state file, so no other local user can take the lock and hold the broker still. DK-13 now states the exit class of a filesystem failure on an operator supplied path and the shape of its error line. The local gate also gained the two commands the conversion template carries, a formatting check and a lint run with warnings denied, and both stand in the workflow beside cargo test and the codepoint scan.

## Encryption amendment, Round 2 slice 1

The probe round tripped one XChaCha20-Poly1305 encryption under associated data and drove a store and a load and a delete against the mock store of the keyring crate. The probe then drove the platform store of this machine, which runs no session bus, and the call answered in about two milliseconds with the platform secure storage failure of the Secret Service store, without a hang and without a panic. The Linux store links against the system libdbus-1, version 1.14.10 on this machine, and the linked binaries load libdbus-1.so.3 from the system library path as ldd records. The development package that ordinarily provides the link symlink and the pkg-config file for that library could not be installed on this machine during the session, so the local build linked through a lane local sysroot supplying exactly those two artifacts against the same system library, and the workflow installs the development package itself. That substitution is a property of this machine and not of the crate, whose manifest names no vendored feature.

This amendment grows the broker by one custody layer that stands between the state file and the document it has always held. Obligations DK-1 to DK-13 stand unedited, and nothing in this amendment changes a grant or a token or an audit entry or a bound that those obligations state. Obligation DK-14 is amended by the replacement paragraph at the end of this amendment. Where this amendment names a key it names 32 bytes drawn from the operating system random source or derived as DK-19 states, and no obligation in this amendment lets a key or a passphrase stand in the state file or in the lock file or in any output.

### Obligation DK-15 covers the envelope

The state file of an encrypted store holds one JSON document whose format field names deadbolt-envelope/1 and which carries exactly the fields format and header and nonce and ciphertext. The payload of the envelope is the canonical bytes of one deadbolt-state/1 document, encrypted whole under DK-16. The header stands in the clear and carries exactly the fields payload and route and store, and one further field kdf when the route is passphrase and no further field when the route is keychain. The payload field names deadbolt-state/1. The route field names keychain or passphrase. The store field holds the store identifier as 64 lowercase hexadecimal characters. The kdf field is an object carrying exactly the fields algorithm and memory and time and salt, where algorithm names argon2id and salt carries 16 bytes in lowercase hexadecimal. The header carries no key material in any form and no value an operator or an attacker can test a candidate key against, the authentication tag of DK-16 being the only key test the format allows. This is covered by tests that render an envelope on each route and check the field sets exactly, that place a further field at any level and check the refusal, and that check the header of a passphrase store against the parameters of DK-19.

### Obligation DK-16 covers the cipher

Encryption is XChaCha20-Poly1305 with a 32 byte key. Every publication draws a fresh nonce of 24 bytes from the operating system random source, and no nonce is derived from the store state or the instant or the document content, and no nonce repeats under one key by construction of its width and its source. The associated data is the canonical rendering of the header object exactly as it stands in the envelope, so the route and the store identifier and the KDF parameters and the payload format name are authenticated with the ciphertext, and an envelope whose header is edited after writing fails authentication. The nonce stands in the envelope as 24 bytes in lowercase hexadecimal and the ciphertext with its tag stands in lowercase hexadecimal. This is covered by tests that publish twice from one loaded state and check the nonce fields differ, that edit one character of the header in a copied envelope and check that authentication fails, and that move a ciphertext between two envelopes and check that authentication fails.

### Obligation DK-17 covers strict reading of the envelope

An envelope that stands must parse as the one format and nothing else, through typed structures that deny unknown fields at every level. A duplicated key, a field the format does not name, a value of the wrong type, a nonce that does not decode to 24 bytes, a store field that is not 64 lowercase hexadecimal characters, a salt that does not decode to 16 bytes, a ciphertext that does not decode or that stands shorter than 16 bytes, and a KDF memory or time outside the ranges of DK-19 each refuse as typed corruption naming the envelope. A route value outside the two the format names, a payload value outside deadbolt-state/1, and a KDF algorithm value outside argon2id each refuse in the same class. Reading the envelope happens before any custody call, and a document matching neither the envelope shape nor the plaintext shape of deadbolt-state/1 refuses as corruption. This is covered by tests that break each named shape in a copied envelope and check the corruption refusal and its order ahead of any custody outcome.

### Obligation DK-18 covers the custody seam

Custody stands behind one trait with three operations, storing a key under a store identifier, loading a key for a store identifier with the three outcomes of the key or a definite absence or a service failure, and deleting a key for a store identifier. The broker core names no platform. The platform backends stand behind the keyring crate, one per platform, being the Keychain on macOS and the Windows credential store whose at rest protection is DPAPI on Windows and the Secret Service over the D-Bus session bus on Linux, and each compiles only on its own platform. The passphrase backend of DK-19 and a fixture backend compiled only into tests stand behind the same trait. Keys cross the trait in a zeroizing type and are wiped on drop. This is covered by tests that drive every custody dependent behavior through the fixture backend, including its absence and its service failure outcomes, and by the build probe recorded in the preamble of this amendment.

### Obligation DK-19 covers the passphrase route

On the passphrase route the key is Argon2id output of 32 bytes over the passphrase and the salt the header records, at a memory cost of 65536 kibibytes and a time cost of 3 and a parallelism of 1 as the constants the writer uses. The reader accepts a memory cost from 8192 to 1048576 kibibytes and a time cost from 1 to 10 and refuses outside those ranges as corruption under DK-17. The passphrase is a byte string of 1 to 1024 bytes, and an empty passphrase fails validation of the request shape before the state is opened. The passphrase enters the command line only through an environment variable it reads once or through a terminal prompt with echo disabled, and never through an argument and never through a file. The passphrase is never stored and never logged and never written to the audit and never echoed by any error. This is covered by tests that derive against a recorded vector at the pinned parameters, that open a store with a wrong passphrase and check the locked refusal, that check an empty passphrase as a caller error, and that grep every output and error for the passphrase and require its absence.

### Obligation DK-20 covers route binding and creation

A store is bound to its route at creation and the header records the route, and no act re-decides it. The command line takes the route as a global option naming keychain or passphrase, required exactly when an act creates a store and refused as a caller error when it stands beside an act against a store that already stands, and a store creating act without it refuses as a caller error and creates no state file. On the keychain route creation draws the key and a fresh store identifier from the operating system random source and stores the key under the identifier before the first publish. On the passphrase route creation draws the salt and derives. An open follows the recorded route only, and a keychain store never opens by derivation and a passphrase store never opens by a keychain lookup. After decryption the inner document store identifier must equal the header store identifier on a keychain store, and an inner document naming an identifier on a passphrase store refuses likewise, each as the transplant refusal of DK-22. This is covered by tests that create on each route and check the header, that offer the route option against a standing store and check the caller error, that omit it at creation and check the caller error and the absence of a state file, and that stand the envelope of one store at the path of another and check the transplant refusal.

### Obligation DK-21 covers the unlock discipline

Every command opens the store through the one path of lock and permission gate and envelope reading and custody and authentication and inner reading, and a mutating act re-encrypts the whole document under a fresh nonce and publishes by the rename discipline of DK-1. The permission gate of DK-11 runs on the state file bits before any decryption. The key and the decrypted document live only in process memory for the length of the act, the key in the zeroizing type of DK-18, and no plaintext is written to any file at any point and no cache stands between commands. A failed unlock writes nothing and records nothing, because the audit trail lives inside the encrypted document, and creates no state file. This is covered by tests that fail an unlock on each refusal class and check the state file bytes unchanged and the directory holding no new file, and that run the audit command after a failed unlock and check the sequence stands as the last successful act left it.

### Obligation DK-22 covers the unlock refusals

An unlock failure is a refusal exiting 1 in one line, and corruption of the envelope or of the inner document is corruption exiting 1, and the two stay distinct. The classes stand in the order the open path meets them. Envelope corruption under DK-17 names the envelope as corrupt. A keychain service failure names the store as locked because the keychain service is not available. A definite absence under the recorded identifier names the store as locked because its keychain entry is missing, and the broker tries no other route and creates no new key over a standing envelope. An authentication failure names the store as locked because the key did not open it, and the same words answer a wrong passphrase and a wrong key and a key derived under edited parameters. A store identifier mismatch after a successful authentication names the store as locked because the envelope does not belong to this store. Inner document corruption names the state document as corrupt under DK-2. No refusal carries a credential value or a token or a passphrase or any key material. This is covered by tests that drive each class through the fixture backend or a copied envelope and check the exit and the line and the unchanged file.

### Obligation DK-23 covers adoption of a plaintext store

A standing plaintext deadbolt-state/1 store is adopted on the first act that opens it under this amendment, with the route option required at that act. Adoption strictly reads the document under DK-2, creates custody as DK-20 states, stamps the inner document store identifier field in the same act, renders and encrypts the envelope, and proves it before replacing anything, by decrypting the rendered envelope in memory and strictly reading the result and comparing it against the loaded document field by field. Only a passing proof publishes, by the rename of DK-1, and no backup copy is written at any point. A crash before the rename leaves the plaintext store intact, and a keychain entry created by an adoption that crashed before publishing is an orphan holding a key to nothing and is named as an accepted residue. The adopting act appends one audit entry naming the route and no key fact, and the act the operator asked for then runs in the same invocation. This is covered by tests that adopt a standing plaintext store on each route and check the file is an envelope afterward and every prior act still redeems, that corrupt the plaintext and check the corruption refusal with no envelope written, and that check the audit sequence stays gapless across the adoption entry.

### Obligation DK-24 covers the limits of the encryption slice

Slice 2 offers no recovery path for a lost keychain entry and none for a forgotten passphrase, and a store whose key is lost is a store that does not open, stated here as the limit it is. The slice does not rotate a store between routes and does not rekey a store in place. The platform backends are proven by the fixture backend and by the build probe, and their behavior against a live platform service is proven only where such a service runs, which is not this machine and not continuous integration, and that residue stands named here until an operator exercise on a machine with the service closes it. The slice adds no binding and no network service, changes no bound of DK-12 and no semantics of DK-3 to DK-9, and does not defend against an attacker who runs as the operator or reads process memory. DK-14 stands amended as follows. There is encryption at rest from Round 2, under the custody of DK-18 and DK-19, with the plaintext store of slice 1 standing behind the permission gate of DK-11 until its adoption under DK-23. The remaining sentences of DK-14 stand as written.

## Rotation amendment, Round 3

This amendment grows the broker by one operation over the standing formats. Obligations DK-1 to DK-24 stand unedited, and nothing in this amendment changes a bound those obligations state or a field of deadbolt-state/1 or of deadbolt-envelope/1 or an end reason the reader accepts. The sentence of DK-14 that names no credential rotation workflow beyond retire and enroll stands retired by this amendment, in the open, and the remaining sentences of DK-14 stand as written.

### Obligation DK-25 covers rotation

Rotation names a predecessor credential and a successor credential and the successor value and the successor scopes, and it stands as one operation under the one lock of DK-1 with one publish. The successor name differs from the predecessor name, because a name is the identity the grants and the audit entries key on and the format carries no incarnation mark. The successor scopes are named in the act exactly as an enrollment names them under DK-3, with no scope implied and none carried over from the predecessor by default, and the command line takes the successor value from a named value file only, as DK-3 states for a value. In the one act the broker enrolls the successor and ends every grant that stands live against the predecessor with the stamp and the reason of DK-4 and removes the predecessor, and no publish stands between those changes, so no state of the store shows the successor standing while the predecessor still stands or the predecessor gone while the successor does not stand. The audit records the act as two entries in the standing shape of DK-9, consecutive in the sequence at the instant of the act. The first carries the kind enroll and the successor name and the outcome enrolled, rotation of the predecessor name. The second carries the kind retire and the predecessor name and the outcome retired, rotation to the successor name. The sequence stays gapless across the pair. A token minted under the predecessor redeems never again after the act, answering revoked as DK-7 names an ended grant, and a grant of the predecessor already dead by expiry at the instant of the act keeps no end stamp and keeps answering expired, as DK-4 leaves it. Rotation mints no grant and no token, and authorisation after the act is by grant under DK-5 alone, against the successor as against any standing credential. A rotation refused against a loaded state records one entry of the kind rotate naming the predecessor and the refusal, and changes nothing else, and request shapes that fail validation before the state is opened are caller errors and are never recorded, as DK-9 states. Replacing a value under a standing name is not built, and neither is a rotation of a store between routes or a rekey of a store in place, which DK-24 already names as later work. This is covered by tests that rotate a credential across a standing population and check the audit pair and the gapless sequence, that redeem a token of the predecessor after the act and check the revoked answer, that rotate a predecessor whose grant already died by expiry and check the grant keeps no end stamp, that refuse a rotation and check the predecessor stands untouched and its live token still redeems, that meet each refusal in its words, and that drive the command line through a rotation and check its output and its exits.
